## 3. Grouping and its guarantees

- `app.wa_turns` (`wt:<uuid>`), `wa_inbound_messages.turn_id`. A turn = all waiting messages of
  one client once quiet for `group_quiet_seconds` (8) or `group_max_seconds` (60) after the
  first, media final and voice transcribed. All time rules on `received_at`.
- **No double processing:** per-client `pg_try_advisory_xact_lock` (a locked client is skipped,
  never awaited) + messages assigned with `turn_id IS NULL` + rows re-read under the lock.
  Proof: wa-db-tests "two claims at the same time: one turn, each message in it once",
  "a locked client is skipped at once (≈60 ms)".
- **Order:** partial unique index — at most one open (`processing`/`pending`) turn per client.
  Proof: "while a turn is processing, the client's new messages wait", "a turn given back is
  retried first: same turn_id, same messages; new ones wait".
- **Nothing lost:** API down → turn `pending` (same id) → retried; stuck `processing` →
  retaken after `turn_stale_seconds`. Proof: hazem-e2e scenarios 3 and 7 (real n8n restart).
- **Lock in PostgreSQL, not Redis** (reason written in `docs/whatsapp-integration.md`).
- The 60-second limit marks unfinished media/transcripts `failed` (TIMEOUT) in the same
  transaction; a later download is refused and its S3 file deleted. Proof: wa-db-tests, and
  it also happened for real during a failed e2e run (the turn left without the photo at 60 s).

## 4. Media and voice

- Flow: PROCESS-EVENT creates `wa_media` (pending) → WA-MEDIA-FETCH → WA-MEDIA-ONE: Graph
  metadata → `wa_media_precheck` (size ≤ `media_max_mb` 50, allowed type, bucket, key) →
  immediate download (3 tries) → sha256 (hex or base64) → S3 via `office-s3` → `wa_media_stored`
  → audio only, behind an explicit check: read back from S3 → OpenAI transcription → `wa_media_transcribed`.
- Buckets: image/document → `office-sensitive`, audio/video/sticker → `office-media`.
- Key `wa/<yyyy>/<mm>/<media row id>.<ext>`. Videos are stored, not transcribed.

## 7. Differences from the prompt and why

1. **S3 key and metadata use the media row id, not the wamid.** A WhatsApp wamid is base64
   that contains the client's phone number; the prompt forbids the number in keys. The n8n S3
   node cannot set custom object metadata, so only the Content-Type is set.
2. **"No `://`" applies to file-reference fields only** (bucket, key, mime type, sha256,
   filename). A client may type a link in a message; refusing it would drop the whole turn.
3. **Transcript up to 16000 characters** (SQL truncates there), not 4096: a few minutes of
   speech exceed 4096 and the turn would be refused (400) and lost. Captions stay at 4096.
4. **A turn also waits for the voice transcript** (within the same 60 s limit).
5. **Extra sub-workflow `WA-MEDIA-ONE`** (one file per execution, so errors stay per file);
   transcription is a step inside it, as the prompt allowed.
6. **Retries:** n8n has fixed waits only: 3 tries, 2 s apart, per HTTP call; plus at most 3
   claims per file in SQL (`TOO_MANY_ATTEMPTS`).
7. **sha256 is compared in n8n** (same rule as `app.wa_media_verify`, which records a mismatch),
   because a database step would drop the downloaded file before the upload.
8. **Test credentials** are removed from n8n's database by fixed id **and** name (the 2.43 CLI
   has no delete), then `n8n-import` restores the placeholders; the before/after "credentials
   not found" line is compared as a PASS/FAIL. The stub never records Authorization values.
9. **Default transcription model `whisper-1`**: documented as a default for the owner to
   confirm on Egyptian samples (T-08).
