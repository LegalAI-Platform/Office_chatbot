## 8. Differences from the prompt / DECISIONS, and why

1. **`hazem.recipients` + `hazem.open_to_all = false` (added).** Nothing in the system enforced
   CLAUDE.md's «never send outside the test numbers» (`whatsapp.test_recipients` is only stored).
   With `responder = hazem` as the default, Hazem would answer any number the day Meta is
   connected. Now he answers only the listed numbers until the owner sets `open_to_all = true`.
2. **The consultation offer is the B-11 text** (owner's decision): DECISIONS defines the offer
   (part 6) but has no general wording.
3. **Urgent = B-09 sentence + the offer + a task** (owner's decision), the booking in TASK 08/10.
4. **«Unclear» falls back to the offer** (owner's decision); the second unclear in a row → no
   reply + a task (`unclear_again` proposed).
5. **The name question once more, before approval, re-sends the B-01 text** (closest approved).
6. **Full name = four parts, «عبد»/«أبو» + the next word count as one** («محمد عبد الرحمن أحمد علي» = 4).
7. **When the AI is down or unsure, a short letters-only message in `awaiting_name` is taken as
   the name**, so a missing key does not block the start of every conversation.
8. **AI stub in hazem-e2e:** `hazem.settings ai.stub_enabled/ai.stub_base_url`, honoured only when
   `ENVIRONMENT=test`, with a dummy key; the real `HAZEM_OPENAI_API_KEY` is never read, sent or changed.
9. **`classify-eval` reads `--file`** (copy the set into the container): Windows PowerShell breaks
   Arabic text piped into docker.
10. **Tasks:** `hazem.pending_tasks` (kinds: `existing_client_message`, `human_requested`,
    `unclear_message`, `urgent_request`, `service_request`, `reschedule_or_cancel`) — a placeholder
    for S-05: no staff, no due time, no panel until TASK 05/07.
11. **Services in this task:** document review → B-16 step 1 + a task; drafting, formal notice
    and Urfi marriage/divorce → proposed text (B-16 without the contact promise) + a task; the
    Urfi questions are TASK 11.
