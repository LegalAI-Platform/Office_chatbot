## 1. What was found before starting

- The backup dumped the databases only: **the client files in storage (receipts, IDs, contracts, voice notes) were
  in no backup.**
- The backups were not encrypted and sat on the same disk as the system.
- `restore` knew office and n8n only (not Chatwoot, not files); no restore had been tried on a schedule.
- The tunnel (Quick and Named) forwarded to **all of n8n**: its login page, its API and the internal send webhook were
  on the internet, not only Meta's webhook.
- A failed backup or healthcheck told nobody; n8n's error workflow alerts only by Telegram, which is not set up.

## 4b. The independent review: every finding fixed

1. A failed listing during the prune could have deleted every file copy → the prune lists to a file, requires
   tonight's manifest in it, and stops on any error without deleting.
2. A new key made the older copies unreadable for the next backup → each key has its own folder (`<key id>`).
3. A restored database had no owner and no CONNECT rights → `restore` copies them from the live one.
4. The edge (and the panel's nginx) kept n8n's / the API's old address after a recreate (502) → Docker's DNS looked up again.
5. The named tunnel could reach n8n directly → the tunnels are on their own network (`tunnel_net`) with the edge only.
6. `nightly.ps1` stopped at the first docker warning on stderr → each step runs on its own.
7. A file deleted by the office during the backup failed the whole run → skipped and counted.
8. A night with no backup at all (PC off) alerted nobody → one «missed» alert a day.
9. `--into-live` could overwrite a file when storage answered with an error other than «not found» → only on 404.

## 4. Differences from the prompt, and why

1. **Files are kept by their content, with manifests**, rather than mirrored: the same receipt sent twice is stored
   once, «a deleted file stays 30 days» is exact (the manifests of the last 30 days name it), and a restore can bring
   back the office's files as they were on any night of the last 30 days.
2. **The edge check accepts n8n's own 404**: while META-WA-INBOUND is inactive (no Meta yet), n8n answers its webhook
   with a JSON 404; the healthcheck checks the answer comes from n8n, not from the edge.
3. **The old healthcheck rule «the backup key cannot read office-sensitive»** became «cannot write» (proposal 1).
